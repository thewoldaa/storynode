# 2026-09-29 — wave 1.5

## What moved

The interface split into a shell and per-area directories, seven defects fixed
in the core library, and one more defect introduced and then fixed in the
attempt to fix the first. 146 unit tests and six CTest tests pass.

## Why the split was its own wave

Wave 1 plans four parallel tasks. Two of them — `canvas` and `inspector` — work
on the interface, and the interface was one file. Two tasks editing one file is
the conflict the harness exists to prevent, and its territory check would have
refused to start them.

The fix is not to relax the check. It is to make the file not shared, and that
work touches the shared file from end to end, so it is one task in its own
wave.

```
ui.html              the shell: markup, message protocol, document state,
                     and the render loop
canvas/              the graph area
inspector/           the property panel
styles/theme.css     the tokens and the chrome
```

An area registers itself with the shell and is called back to render. The shell
never calls an area by name; an area never reads another area's state.

## The asset problem, and why it shaped the design

The page cannot load its own assets. `NavigateToString` gives it an opaque
origin, so a `<script src>` or a `fetch` to a sibling is refused, and there is
no local server to ask instead.

So the build embeds every asset as a resource and the host inlines them into
the shell. The list is generated from a glob. That matters more than it sounds:
a hand-written list would be a shared file every task must edit, which is the
same conflict the split exists to remove, one level down.

The acceptance test for this was written before the fix and run against it:
adding `canvas/zz-probe.js` made it load — glob, manifest, embed, execute — with
`git status` showing nothing changed outside `canvas/`.

## Defects found by review

A review pass over the core library found seven real defects. The two that
matter most:

**`SaveToFile` could destroy both files.** It deleted the original, then
renamed the temporary into place. Between those two steps neither file exists,
and if the rename fails — a scanner holding the temporary, a read-only
directory — the original is already gone and the caller is told only "cannot
replace". `std::rename` does not overwrite on Windows, which is why the delete
was there in the first place.

**An endpoint's unknown keys were deleted on save.** Every level of the
document preserves keys this version does not recognise, so that a file written
by a newer build survives being opened and saved by an older one. Every level
except the endpoint. A key added there by a newer build — a condition, a delay
— was gone the first time this build saved the file.

The others: two undefined double-to-integer conversions from a range guard
written on the wrong side of the cast; a format version of 4294967297
truncating to 1 and passing the "not newer than this build" check; `NextId`
counting in `int` so an id near the limit could overflow into a duplicate; and
a fractional format version being truncated and accepted.

## The defect I introduced while fixing one

The first attempt at the safe save replaced `std::rename` with
`std::filesystem::rename`, on the assumption that the standard library version
overwrites. It does not — same limitation, same error. Saving over an open
document stopped working entirely, and the test suite caught it on the next
run with `Access is denied`.

The fix is `ReplaceFileW`, which is the Windows API for exactly this. The
destination has to exist, so a first save takes a plain rename instead, and
both paths are now pinned by tests.

That is the second time in this task that running something caught what reading
did not. The first was the resource name quoting below.

## Two resource bugs that look identical from outside

Both of these produce the same symptom: the asset is in the binary, cannot be
found, and the application shows a blank window with no error anywhere.

**`rc.exe` does not treat quotes as delimiters around a resource name.** It
stores them as part of the name. A resource written as `"UI.HTML"` has a
nine-character name; `FindResourceW(L"UI.HTML")` looks for seven and finds
nothing. Confirmed by walking the PE resource directory and reading the name
length field, after two wrong guesses about what else it could be.

**CMake treats a backslash in a string as an escape introducer.** A Windows
path written into a generated file silently loses characters: `\ui\assets`
arrives as `\ui` plus a BEL, `\styles\theme.css` as `\styles` plus a TAB. The
resource compiler then reports "file not found" for a path that is visibly
correct in the source.

`probe_resources` now exists because of these. A resource that is in the binary
and not findable by name is invisible otherwise, and a diagnostic tool that
lies — the first version of the probe was itself built without the resources
and reported everything missing — is worse than no tool.
